单元补充讲解

完整参考原稿，按需回查。旧站号可能不同，当前任务与验收以课堂为准。

按任务查阅的补充讲解

各节供对应知识单元单独引用，不要求从头通读。示例是教学说明；工程是否成功，以学生实际运行和记录为准。

四句话限定自己的首作

先写四句：玩家反复做什么；什么结果表示做得好；什么时候结束；怎样重新开始。例如：左右移动篮子接光点；接到一次加一分；漏掉三次结束；点重开后分数和漏接数归零。核心操作也可以是点击、拖放或选择，不需要强行做成接物游戏。

再写一项第一版不做的内容，例如联机、商店或多结局。判断标准是：删掉它以后，上面四句能否成立？能成立，就先删。请同学只看这四句复述一次；如果他还不知道怎样操作或怎样结束，先把句子补清楚，再增加功能。

工程文件与两种备份

Godot工程以project.godot为入口，场景、脚本和被引用的图片声音要一起保留；.godot通常是编辑器生成的缓存，不把它当作唯一资源来源。用新的目录或设备打开副本，才能发现遗漏资源。Git只记录已经提交的内容，推送才传到远程；没有保存进Git的内容不能假设能从历史找回。

网站里的姓名、学习记录和问题是另一类数据。在个人菜单的存档管理导出统一备份，保存JSON文件；它不会替你备份Godot工程。需要验证恢复时，使用独立浏览器测试环境，先备份原记录，再预览导入，不能拿自己唯一的记录做破坏性练习。合格证据是：能分别指出学习备份文件和可重开的工程副本。

计时生成与对象清理

编辑器里拖入场景，是预先摆放；运行时刷出对象，需要代码创建实例并把它加入场景树。最小关系是：Timer触发timeout → 运行instantiate创建一个对象 → add_child挂到明确的父节点。先不加随机位置，确保一次触发只增加一个对象，再加入位置变化。

清理要有条件：命中、越界或寿命结束时释放对象；queue_free安排在安全时机移除，别再把旧引用当作有效对象使用。结束游戏时，停止继续生成，并明确是否清理现有对象。换条件核对：缩短计时间隔、结束后等两秒、重开三次，观察对象数与生成频率是否符合预测。相关API看官方“Nodes and scene instances”的Creating nodes、Instancing scenes、Freeing nodes，不必先读完整节点类手册。

信号到计分与重开的完整关系

把关系分成三步：物品只报告“我被接到了”；主场景决定分数加多少；界面把当前分数显示出来。这样物品不必知道Label在哪里。先画发送者 → 信号 → 接收函数 → 分数 → 界面，再在工程里找每条箭头对应的连接或调用。

重复计分不一定是算术错误，也可能是物品触发两次，或一次事件被两处处理。连接时机与对象寿命需要一起看：旧场景是否已经释放，新一轮是否再次给同一对象连接？不要简单地到处断开信号。换条件测试连续拾取、结束后拾取和连续重开三轮；每轮起点、加分次数与结束行为都应明确。

反馈要连回实际事件

动画、声音和界面反馈围绕同一个事件安排，例如拾取后物品消失、分数改变、短音播放。先不追求三种效果同时做：选一个原来难以察觉的结果，只补一种反馈，让同学判断是否看懂了。

再排查触发次数与结束时机：动画是否每帧重播？声音是否叠加？重开后旧声音是否继续？动画文档只查播放与帧组织；音频文档只查对应播放器与播放方式。没有素材授权或音量规格时，先用自制占位音，不让“能播放”代替素材可用性核对。

界面布局与键盘焦点分开验证

容器解决控件在不同宽度下怎样排列，焦点解决按键交给哪个控件。先用一个标题、两个按钮做界面，在窄窗口检查文字不截断、按钮仍能点击；不要一开始手动固定所有坐标。

接着只用键盘：Tab能否到达操作；Enter能否确认；关闭弹窗后是否回到合理位置；游戏结束时焦点是否落到重开按钮。布局正确不等于焦点正确。换条件检查长标题、320px窄屏和鼠标离开三种情况；只补当前出现的故障，不先搭复杂UI系统。

数组字典与资源各管什么

数组适合一组有顺序的内容，例如关卡列表；字典用键找到值，例如物品ID对应价格；Resource适合把编辑器可配置的数据保存成资源。它们不是必须同时使用的三个框架。先列一个实际查询：我要按哪个键找到什么值，谁有权修改它？

用两种物品做最小测试：改变一个的价格，观察另一个是否也变了。如果共享了同一资源，意外联动可能来自共享引用。先区分配置与本局可变状态，再决定是否复制或另存状态；不要通过复制所有脚本掩盖问题。

后台加载与使用时机

同步加载简单直接；后台加载适合确实阻塞当前体验的大资源。先测切换前后的等待发生在哪里，不能看到卡顿就先加线程。最小方案是：开始请求 → 检查进度或状态 → 成功后取出资源并切换 → 失败给出返回或重试。

不要在资源尚未完成时直接当场景使用，也不要把同一个切换请求重复触发。换条件测试第二次点击、资源路径错误与取消切换；保留当前可用场景，说明自己未覆盖的设备和大资源情况。

关卡与数值先做小对照

关卡练习先只验证一个规则：让玩家先安全看见障碍，再用刚学会的操作通过，随后稍微改变距离或顺序。记录他在哪里停下、误解了什么；不要用“我觉得难度合适”代替观察。

数值练习一次改一个变量，例如移动速度或出现间隔。先写预测，再在同一条件下比较两个值，记录完成时间、失败位置或其他与目标直接相关的结果。成长曲线至少说明起点、增长与上限，防止奖励过快或永远追不上目标。Resource能保存数字，但不会自动替你决定合理数字。

文案与无障碍的最小检查

文案先回答玩家此刻需要知道什么：目标、操作、失败原因和下一步。用一句短提示替换长段世界观，请第一次接触的人复述并操作。叙事只在项目确实需要时扩展。

无障碍先消除当前障碍：重要状态不只靠颜色区分，文字在背景上可辨，音量可调或能静音，按钮和必要操作可到达。分别用关闭声音、不同窗口宽度、只用键盘来检查。不是要求首作实现所有辅助选项，而是明确当前目标人群能否完成核心循环以及尚未支持什么。

随机内容与实时AI先证明有价值

随机生成先定义不可破坏的规则，例如起点到终点必须连通、奖励不能生成在障碍里。固定种子便于复现，先用少量可人工检查的样本，再比较相同种子是否得到同样结果。换一批种子检查边界；少量样本通过不等于证明永远不会失败。

实时AI先问：删掉模型调用，玩法损失了什么？若只是固定提示语，静态文本可能更合适。确需调用时，画出输入 → 请求 → 等待 → 校验 → 游戏效果，定义超时、费用上限与替代内容。服务端凭据不能塞进公开网页。先用模拟返回验证流程，再考虑实际服务；本课程不自动替学生调用付费模型。

职责接口与方案取舍

一张职责表先写谁拥有数据、谁可以改变数据、谁只显示结果。以拾取为例：物品报告事件，Main维护分数，HUD显示分数；事件可带物品ID和分值，但HUD不再偷偷累加一份分数。

接口至少写输入、输出、调用时机与失败处理。比较两个方案时，用同一个变化验证：如果换界面，哪些地方要改？如果删掉物品，谁负责清理？先选能满足当前约束、改动影响可解释的方案。模块越多不等于架构越好；暂时重复的两行代码也不一定值得提前抽象。团队协作时先对齐这个约定，再用PR检查实现是否符合约定。

素材一致性与版本交接

先为当前一种素材定规格：尺寸、透明背景、命名、动画帧数或音频时长、来源许可、在工程中的使用位置。生成一张或一个声音导入验证，成功后才批量做。风格描述不是规格，实际能否显示和播放也必须检查。

每次交接写清源文件、处理后文件、导入设置、当前使用版本与许可。不能确认授权的资源先替换为占位素材。与AI协作时给一张可用样本和明确约束，再比较新素材；不要把几十个没有检查的文件一股脑放进工程。

动画与本地化的制作验收

角色动画先确定状态与触发，例如静止、移动、受伤；每个状态有入口、退出与优先级，再安排帧或动画片段。换条件检查快速切换和结束重开，确认没有旧动画覆盖新状态。

本地化先把显示文本与逻辑分开，确定语言切换入口，再用一条更长译文检查按钮、换行、字体和缺字符。AI翻译只是候选，操作说明和关键规则需人工核对。第一款游戏不必先翻译全部内容，可先用最关键的三处文本验证管线。

真实试玩与调试各解决什么

调试解决可复现的运行问题；试玩还要发现“没有报错，却让人误解”的地方。给试玩者一个目标，先不解释操作答案，观察他实际做了什么。记录版本、任务、行为、原话或时间点，把观察事实和自己的推测分开。

先处理阻止开始、无法继续、严重误导的问题；建议先保留，不因一个人随口提议就改方向。修复后用相同目标复验，再检查相关行为没有被破坏。AI可以帮助整理记录和提出假设，不能代替没有发生的真人试玩。

架构演化与回归边界

先描述具体压力：新功能需要反复跨模块改动、同一数据有多个主人，还是性能确实不够？留一个旧行为的验证步骤，再只调整一处职责或接口。用同一任务对比改前改后要动哪些地方。

自动检查优先保护明确的规则和故障复现，不承诺自动判断“好玩”。变更后运行原复现、相邻行为和完整核心循环；保留有效版本，失败时能退回。大改前先写迁移和回滚办法，不让“重构”成为没有验收的重写。

作品申请的三个状态

先在自己的Pages网址打开游戏，从开始玩到结束重开，确认交付的是可玩页面。回到本站“同学作品”，选择“提交我的作品申请”，填写姓名、作品名、简介、操作、可玩网址与版本；源码网址和封面为可选项。预览时检查可玩地址没有误填成仓库首页。

本站草稿只在本机；前往GitHub仍需本人登录并最终提交。提交后保存Issue地址，等待教师核验并加入共用清单；打开GitHub或保存草稿都不等于已上架。姓名与申请内容会公开，请只填展示需要的信息。更新时说明稳定作品ID、旧版本、新版本和修复内容，避免同一作品反复生成新条目。

演示视频让人看懂玩法

先写三个镜头：怎样操作；操作产生什么反馈；目标或结束是什么。每个镜头从当前可玩版本录制，不用未来构想和生成画面冒充已实现功能。先录十几秒的粗版，不急着做片头和特效。

让没玩过的同学看一次，再请他复述操作和目标；讲不清就删掉无关画面、补关键反馈或加短字幕。截图优先展示实际交互和清晰界面。视频、封面和可玩网址标记同一个版本，游戏改了以后重新核对说明。

第二平台与第二渠道先分清

平台是实际运行环境，例如浏览器或桌面操作系统；渠道是玩家从哪里获得同一个版本，例如Pages或另一家托管服务。选修时先写清要解决的是哪一个问题。第二平台不能直接照抄Web导出：选定目标后，查Godot对应平台的官方导出说明，并在那个环境亲测输入、声音、结束与重开。

第二渠道先用同一套完整Web导出文件，核对目标服务是否支持所需文件、HTTPS、嵌入及更新方式，再上传一个最小测试。记录新可玩网址和版本，与原Pages逐项对照。未选择服务时先不注册、不上传；不把“打开了服务首页”算作发布。

国内小游戏先做可行性验证

浏览器里的Godot Web游戏不能因为有HTML就假设能直接变成微信或抖音小游戏。先选一个平台，核对当期官方运行环境、包体与接口要求，再查对应Godot版本的导出或适配方案、维护情况及许可；不要直接执行面向手写HTML的旧adapter提示词。

先用一个画面、一个输入和一个声音验证实际设备路径，记录哪些文件由什么工具生成，失败在哪里。若没有经过验证的适配路径，保留Pages交付，专题记录为“可行性尚未确认”，不能勾成上架成功。付费、实名或正式上架材料由本人处理。

发布后的投入判断

先区分故障、使用困惑和新功能建议。为当前版本列出实际反馈人数、复现证据、修复时间和预计收益；没有真实数据的地方标为假设。不要拿Issue数量、浏览次数或点赞直接推断收入和留存。

每次只选一个决定：修阻塞问题、做一个小验证、暂缓需求或结束维护。写下判断依据、投入上限和下一次观察条件；更新后检查是否真的改善。归档时保留源码、可玩包、操作说明、素材许可和已知问题，副本能重开才算可交接。

克隆到第二副本验证同步

先用GitHub Desktop克隆自己的练习仓库：核对账号、仓库网址、保存位置和当前分支。打开本地README，只改一句说明，先在Changes看差异再提交；Push origin把这个提交传到远程。浏览器打开同一分支，确认变化已经出现。

在另一目录克隆同一个仓库，核对相同文字与提交。之后回第一副本再改一句并推送，在第二副本Fetch/Pull后比较。没有第二台电脑也可以用两个独立目录练习，但要如实记录。出现冲突先保护未提交工作，不能靠删除整个目录解决。命令行只是替代操作方法，本节不要求两套都做。

用历史定位一次退化

先写固定复现条件，例如“按一次重开后捡一枚物品”。找到最近一次能正确运行的提交和第一次确认错误的提交，在独立副本比较这段历史的差异；保持输入和测试步骤一致，否则无法判断修复来自哪里。

记录怀疑的变化、验证依据和最终修复提交。历史很多时可以逐步缩小区间；自动bisect适合已有稳定判定步骤时再查，不需要为了本任务学完全部Git排错命令。没有提交过的变化不在这条历史中。

问题卡与看板的最小用法

问题卡写目标或现象、预期、复现步骤、版本与完成条件。修复卡不能只写“游戏坏了”，例如“v0.2结束后按重开，分数没有归零，预期为0”。开卡后先确认能否复现，再安排处理。

需要同时跟踪多项任务时，再使用Projects把这些已有Issue放到待做、进行中、已完成。完成列表示已按验收核对，不表示“AI说改完了”。本节先维护一张卡的状态流转；看板入口和配置通过官方Issues文档中的Projects链接查阅，不再平行维护另一份重复清单。

碰撞先看形状层与运动

画面中的贴图不等于碰撞形状。先用一个CharacterBody2D和一个静态地面验证阻挡，检查碰撞形状是否启用、位置是否贴合、层与掩码是否能相互检测。把碰撞形状显示出来，再解释为什么看似接触却穿过去。

角色运动、检测区域和刚体受力不是同一种用途。先选择当前任务需要的一种节点，按相应运动方式测试，不同时照搬多套控制脚本。换条件把地面移开、改变检测层、提高速度；一次只改一个因素，记录哪种变化改变了结果。

比较模型时固定同一任务

用同一份目标、上下文、允许改动范围和验收步骤比较两个工具或模型。先规定成功标准，例如功能实际可用、改动范围可审、没有额外依赖，再分别独立执行；不要把第一份答案贴给第二个以后称作公平对照。

记录实际运行结果、需要补充提示的次数、等待和花费；没有的数值不编造。选适合当前任务的方案，不用一次实验推断所有能力。若两者都过不了检查，先审查任务和环境，不只追求更换模型。

叙事分支必须有条件与结果

先写一个两选项的小片段：玩家知道什么、能选什么、选择改变哪个状态、后续哪里使用这个状态。例如救不救商人改变信任值，下一次见面读取它决定对话；不要只写两段不同台词却声称有系统性后果。

用表写“前置条件—选项—状态变化—可见结果”，检查每个分支是否可达、是否有回到主循环或结束的路径。AI可以帮忙补台词和查漏，分支规则由你实际走通。先验证两个选择再扩展，避免剧情树无限增长。

从需求读出架构约束

画模块前先列：必须实现什么、第一版不做什么、在哪个环境运行、现有工程不能破坏什么。例如浏览器单人小游戏、不能依赖服务端、允许更新界面但不能让旧分数残留。这些约束会影响状态放哪里、资源怎样加载、失败怎样返回。

把“将来可能需要”与“已经确认必须支持”分开。不确定项先做最小实验：若换场景就丢数据，先验证状态寿命，再决定是否引入跨场景管理。最后将每个模块或接口连回一条需求；无法说明用途的先不加。

用同一架构方法处理生活任务

以复习计划为例：输入是课程要求与错题，处理是按缺口分组并选当日任务，输出是一份可检查的小练习结果；反馈是哪些错误仍然存在。学生自己决定目标与时间，AI可以整理错题、给提示，但结果要由实际练习证明。

明确数据放在哪里、谁负责更新、失败怎样处理，例如没完成时调整任务量而不是自动伪造打卡。先人工跑一轮，再判断哪一环值得自动化。生活系统同样需要输入、职责、接口、反馈和边界，不必照搬Godot节点或写成软件。

拆解主场景与运动链

固定工程按project.godot → game_singleplayer.tscn → Level/Player追入口。先运行项目，再比较运行当前场景，确认自己看到的是哪个入口。找player/player.gd和player/player.tscn，将一次输入、速度变化和碰撞现象连起来；文件名只是定位线索，实际节点与连接仍要在编辑器核对。

先预测持续按住、松开、再按一次的区别，再在副本改一个参数。记录主场景、相关脚本位置和实际结果，不要求读完整个仓库。基线为原导读记录的固定Platformer提交；后续版本路径变化时先停下核对。

拆解一次生成与反馈

只追一颗子弹：player/gun.gd什么时候发射，player/bullet.gd怎样运动和处理命中，enemy/enemy.gd什么时候接收结果。记录生成的父节点、对象引用和移除条件；不要看见一个queue_free就假定整条链已经没有残留。

只追一次反馈：先在游戏里观察，再找相应AnimationPlayer或音频节点及贴图、资源，倒查是谁触发它。暂停或结束时再做一次，区分“没有触发事件”和“触发了但没有呈现”。使用原工程的实际文件作证据，不把自己的猜测写成作者原设计。

拆解暂停并确认缺口

沿game.gd与gui/pause_menu.gd追暂停和恢复，检查哪些对象停止、哪些按钮仍可响应。固定Platformer的玩家无敌，只有封闭关卡；它没有为本课程提供完整玩家受伤、胜负与重开链，不能把敌人受伤当作玩家生命系统。

先写明确缺口，再只补当前需要的一项：参考GDQuest的player.gd受伤与health_depleted以及game.gd结束处理，或使用自己的原型。比较暂停、结束、重开的状态变化并实际运行，不重做整个第二项目。存档是另一个专题，不能假定主例已有。

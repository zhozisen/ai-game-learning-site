# 通关回顾：用作品证明自己学会了什么

先完成01发布和05维护。目标是让别人能玩、自己能解释和改进；不要求首作盈利，也不要求答题满分。概念题用于诊断，最终工程由教师结合证据检查。

## 毕业证据表

| 站点 | 提供什么 | 教师抽查什么 |
|---|---|---|
| 1 Git | 提交历史与恢复练习 | 找回一个练习文件并解释变化 |
| 2 Godot | 六步观察和小项目 | 找场景、读短脚本、解释输入信号、定位错误 |
| 3 AI | 任务卡、流程表与检查记录 | 哪些由自己判断，怎样核查AI |
| 4 拆解 | 一份体验与工程证据报告 | 观察和推测能否分开 |
| 5 策划 | 一页设计与首版范围 | 体验假设、功能标准和不做清单 |
| 6 制作 | 可玩作品与独立功能任务 | 实际操作、解释改动、边界复验 |
| 7 发布 | 可运行版本、说明、试玩与复盘 | 他人能按说明运行，反馈处理有依据 |

暂未完成的项标“待补：具体任务”；只补薄弱项，不强迫全站重学。读完、答题通过和独立完成是不同层级。网站点亮与雷达作为学习辅助，不冒充教师已经验收。

## 自测：边回答边找自己的证据

1. 工程文件、导出包与网站学习进度分别存在哪里？
2. 改坏后怎样找回练习文件，并保护尚未保存的工作？
3. 场景和实例有什么区别？指出自己的实例。
4. 解释短脚本的一次输入、条件和状态变化。
5. 输入或信号不生效时先查什么？
6. AI说修好了，你如何确认？
7. 从目标到反馈的AI协作流程是哪几步？
8. 玩家实际做了什么，与你的原因猜测有什么区别？
9. 第一版为什么只做这些内容？
10. 有重开按钮能否证明玩家想再玩？还需怎样观察？
11. 一个功能怎样检查正常、重复和结束后的行为？
12. 图片显示正常为何还要单独检查碰撞？
13. 编辑器中能运行为何不能直接代表导出通过？
14. 选一个真实反馈，说明修复或不修改的依据。

答不出回对应站补练，不设“答对10题即毕业”的替代标准。

## 收尾

保存工程、对应Git版本、资源来源、运行说明、已知问题和试玩记录。验证备份能打开；网页进度另外导出。复盘写三点：自己真正会了什么、还有什么依赖帮助、下一次先改进什么。再开始第二款规模适当的作品。

07_从策划到结构与任务

完整参考原稿，按需回查。旧站号可能不同，当前任务与验收以课堂为准。

把一页策划变成可执行的小工程

前置：完成02、03，能说明核心动作、首版范围与三条检查标准。沿用第2站已运行的小项目，不照抄复杂背包肉鸽项目。

开工前先做三个判断

给谁玩、玩什么：选择真实可接触的一类玩家，描述他们的设备与操作经验。对标一个自己实际玩过的作品，指出借鉴的核心循环，不复制素材。热门不等于适合本班同学，也不等于有商业需求。

是否有趣：列一个可观察的体验问题，让原型验证。例如“第一次玩的同学是否能在不听讲解时理解拾取目标”，不是只写“很好玩”。

是否做得完：列自己已会的部分、未知技术、资源和时间。先实验最大的未知点，超出范围先删减。商业判断基础是理解给谁提供何种价值和成本；深度定价、获客及AI原生玩法仍放06选学，不把收费作为首作门槛。

先画职责与联系

主资料：[Godot官方 场景组织](https://docs.godotengine.org/zh-cn/stable/tutorials/best_practices/scene_organization.html)，先读职责单一、场景关系与信号连接的讨论。中文版本选择器可能跳转，应与实际版本核对；代码按本机版本验证。复杂依赖注入示例先跳过。

以简单拾取游戏为例，下面是示意，不是要求所有游戏使用同一文件结构：

| 部分 | 负责什么 | 如何联系 |
|---|---|---|
| 主场景 | 组织本局开始、结束和重开 | 创建所需对象、连接事件 |
| 玩家场景 | 接受输入、移动 | 按约定提供行为和状态 |
| 可拾取物场景 | 被拾取后的本地表现 | 通知发生了拾取，由负责计分的部分处理 |
| 分数状态 | 保存当前分数 | 按规则变化，不由Label文字反推全部状态 |
| 界面 | 显示分数和按钮 | 接收显示更新，按钮发出操作请求 |

画图时写清数据由谁修改、事件由谁发出与处理。小工程可以合并职责相近部分；不必每一行都建一个类。避免两个脚本同时认定自己是唯一计分者，造成一次拾取加两次分。

从结构图拆任务

需求：拾取后加分，达到目标进入结束界面，并能重开。先核对已有移动与拾取，再依次实现“拾取反馈与计分”“结束条件与界面”“重开状态恢复”，每步保留可运行版本。若一个小变化必须跨场景和脚本，一张卡仍可包含多个文件。

任务卡沿用第3站模板：目标、前置、输入、范围、预期行为、边界、恢复点。先做技术上不确定又影响核心循环的部分，不先批量生成整套美术。测试与版本管理贯穿每一步，美术与程序可按依赖配合，不是全部代码做完才允许美术。

练习与测试

练：用自己的项目补一张职责图，给一项功能写两到四张有依赖的任务卡；说明第一张怎样运行检查。沿用一页GDD，不重写整套策划。

测：新增“最高分”后，本局分数与最高分应该由谁保存、什么时候变化、重开时哪些保留？画出影响范围并说明验证方法。不能只把“重开全部清零”的旧步骤复制过去，也不要求为了这一个需求先引入复杂数据库。

交付：一页设计、结构图与任务卡之间能相互对应。教师核对范围与技术判断后进入第6站，执行和试玩结果再反过来修订设计。
